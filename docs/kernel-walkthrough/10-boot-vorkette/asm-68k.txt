=== Reset-Vektortabelle (Datei-Offset 0x00, roh) ===
00000000: 0000 4a00   ; Vektor 0 (initialer SSP)        = 0x00004A00
00000004: fe00 0494   ; Vektor 1 (initialer PC / Reset)  = 0xFE000494
00000008: fe00 1b0e   ; Vektor 2 (Bus Error)             = 0xFE001B0E
0000000c: fe00 1b14   ; Vektor 3 (Address Error)         = 0xFE001B14
00000010: fe00 1b1a   ; Vektor 4 (Illegal Instruction)   = 0xFE001B1A
00000014: 0000 041e   ; Vektor 5 (Zero Divide)           = 0x0000041E  <- "niedrige" Adresse!
00000018: 0000 0428   ; Vektor 6 (CHK)                   = 0x00000428
...                    ; Vektoren 6-8,10-30: durchgehend "niedrige" 0x0000xxxx-Adressen
00000024: fe00 1b20   ; Vektor 9 (Trace)                 = 0xFE001B20  <- "hohe" Adresse
0000007c: fe00 1b08   ; Vektor 31 (Level-7/NMI)          = 0xFE001B08  <- "hohe" Adresse

BEFUND: Vektor 1 zeigt auf 0xFE000494 -- das IST exakt Datei-Offset 0x494.
Damit ist die Basisadresse der ROM-Abbildung im finalen Speicherlayout
0xFE000000 zweifelsfrei bestimmt (Datei-Offset + 0xFE000000 = Ziel-
adresse). Gleichzeitig liest die CPU dieselbe Tabelle beim Reset an
Adresse 0x00000000 -- klassischer 68K-"Overlay"-Bootmechanismus: das ROM
ist beim Reset zusaetzlich an Adresse 0 gespiegelt, bis der Reset-Code
selbst die Spiegelung abschaltet (s. u., Bit-4-Test bei 0x5EA).
Vektoren, die dauerhaft gueltig bleiben muessen (Reset selbst, Bus-/
Address-/Illegal-Instruction-Error als frueheste Diagnose, Trace, NMI),
zeigen konsequent auf die "hohe", dauerhaft gueltige ROM-Adresse; die
uebrigen (Zero Divide, CHK, TRAPV, Line-A/F, ...) zeigen auf "niedrige"
Adressen -- plausibel Platzhalter, die erst durch den spaeter geladenen
Kernel (Thema 01) mit echten RAM-Handlern ueberschrieben werden.

fe0005d0: subi.l #0x9e0,D4        ; D4 = 0x5600-0x9E0 = 0x4C20

fe0005d8: subq.l #0x1,D4

;     der System-Global-Bereich, den der Kernel beim eigenen Start bereits
